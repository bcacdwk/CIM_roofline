\section{Proposed Resident-Streaming Roofline}
\label{sec:model}
\subsection{Workload Demands and Hardware Throughputs}
The classical Roofline describes a workload by its operation count (OPs) and data-transfer volume (Bytes). Following the operand roles in Fig.~\ref{fig:operand-roles}(b), we instead describe a CIM workload through its streaming inputs and resident writes. We count both over an explicit \emph{workload window}, which specifies the work under analysis and the resident state at its start.

We measure streaming calculation by the logical input bytes evaluated using resident state, with each evaluation (MAC) producing the specified outputs (partial sum). The streaming demand $Q_S$ is the number of such bytes served at the chosen logical input boundary; it thus represents completed calculation work rather than input/output traffic alone, and it is directly comparable with resident writes. The resident demand $Q_R$ is the number of logical bytes written within the window to load or update the resident state that this work requires. An initial load completed before the window is excluded; all updates and reloads within the window are counted. The resident operand may be a static weight or the KV cache of earlier tokens.

We characterize two hardware services, streaming-input calculation and resident-state loading, by their throughputs. The streaming throughput $\rho$ is the maximum rate, in logical input bytes per second, at which the hardware completes streaming calculations and produces the specified outputs. The resident throughput $\tau$ is the maximum rate at which logical resident bytes become ready for calculation. Both rates refer to the CIM hardware under analysis, with bytes counted at the same interfaces and operand precisions used for $Q_S$ and $Q_R$, respectively. We define Streaming Intensity and average streaming-input throughput as
\begin{equation}
  \SI=\frac{Q_S}{Q_R},\qquad
  P=\frac{Q_S}{T}\quad[\Byte/\mathrm{s}],
  \label{eq:definitions}
\end{equation}
where $T$ is the window duration, $P$ is the average streaming-input throughput over the window, and $\SI$ is the streaming demand per byte of resident write.

The workload's $\SI$ describes the relative demand for streaming calculation and resident writes, while $\rho$ and $\tau$ describe how quickly the hardware can perform each. The throughput bound therefore follows from the time required to complete these two kinds of work.

\subsection{Theoretical Model and Correspondence}
Fig.~\ref{fig:roofline-comparison} compares the proposed resident-streaming Roofline with the classical model. Streaming calculation and resident writes require at least $Q_S/\rho$ and $Q_R/\tau$ of service time, respectively. The execution must satisfy both constraints, giving
\begin{equation}
  P\leq\min\!\left(\rho,\tau\cdot\SI\right).
  \label{eq:roofline}
\end{equation}
The two service requirements balance at the hardware ridge $\SI^*=\rho/\tau$. A workload is resident-bound on this hardware when $\SI<\SI^*$ and streaming-bound when $\SI>\SI^*$.

The same bound can be expressed in the familiar GPU-style operation and byte rates. For a window containing $O$ useful operations, the equivalent compute throughput $\pi_{\mathrm{eq}}$ and aggregate bandwidth $\beta_{\mathrm{eq}}$ of CIM are
\begin{align}
  \pi_{\mathrm{eq}}
    &=\frac{O}{Q_S}\cdot
      \min\!\left(\rho,\tau\cdot\SI\right),
      \label{eq:equivalent-compute}\\
  \beta_{\mathrm{eq}}
    &=\left(1+\frac{Q_R}{Q_S}\right)\cdot
      \min\!\left(\rho,\tau\cdot\SI\right).
      \label{eq:equivalent-bandwidth}
\end{align}
These are workload-specific projections of the same upper bound: $\beta_{\mathrm{eq}}$ counts the combined logical volume $Q_S+Q_R$, rather than traffic through a GPU memory interface.

Whether a hardware metric is workload-independent depends on the coordinates used to describe it. In GPU, compute and memory units provide distinct services, matched to operation counts and data-transfer volumes. In CIM, storage and computation are combined, but streaming calculation and resident-state loading remain distinct services, matched to streaming-input and resident-write bytes. Each model therefore decomposes hardware services and workload demands along the same dimension---by hardware function for GPUs and by operand role for CIM. This alignment gives each architecture its native capabilities, $(\pi,\beta)$ or $(\rho,\tau)$, which are fixed for a given configuration. Translating between the two descriptions requires additional information: how many operations the inputs support and how much resident writing is needed. The hardware remains unchanged, but its projected metrics become workload-dependent because the relationship between operations and operand bytes is determined by the workload.

\subsection{Analytical Case Studies}
Consider an illustrative 28~nm SRAM ACIM macro serving a logical $128\times128$ INT8 matrix, with preloaded weights and an assumed input-vector service interval $\Delta_S=10$\,ns. Each matrix-vector multiplication consumes 128 input bytes and performs $2\times128^2$ useful operations, counting two operations per MAC. Thus $Q_R=0$ and $O/Q_S=256$\,OP/Byte, giving
\begin{equation}
  \begin{aligned}
    \beta_{\mathrm{eq}}
      &=\rho=\frac{128\,\Byte}{10\,\mathrm{ns}}
        =12.8\,\mathrm{GB/s},\\
    \pi_{\mathrm{eq}}
      &=(256\,\mathrm{OP}/\Byte)\cdot\rho
        \approx3.28\,\mathrm{TOPS}.
  \end{aligned}
  \label{eq:macro-example}
\end{equation}
The familiar TOPS value is therefore the streaming ceiling expressed in operation units.

We next evaluate $\SI$ for GEMM workloads. For a logical matrix $W[N,K]$ with $N$ outputs and $K$ inputs, let $U$ be the number of input vectors served after one complete load, including the first use and allowing reuse across batches or requests. With one byte per input and weight element, $Q_S=UK$, $Q_R=NK$, and $\SI=U/N$. For full-load time $T_R$ and vector service interval $\Delta_S$, the corresponding balance occurs at $U^*=T_R/\Delta_S=N\SI^*$.
